# 星环算力调度系统：SDD 开发计划流程书

## 一、目标与交付物

本项目使用 **C++17** 实现交互式调度器。每个 tick 先处理平台事件，再回答对账题，最后输出合法调度指令。验收顺序固定为：

1. **协议正确**：持续读写交互、每轮刷新输出、第 `T` 轮后退出。
2. **对账正确**：七类对账题在事件处理后、指令执行前均与本地评测程序一致。
3. **指令合法**：包括同一 tick 内多条指令按顺序执行后的状态。
4. **利润改进**：在前三项稳定后，以本地生成的多组世界比较策略。

计划将来落为仓库中的 `docs/开发计划.md`，并维护题面规则、数据结构、测试记录和策略实验的对应关系。仓库地址：<https://github.com/Cool-11/Computational-Power-Scheduling>（SSH：`git@github.com:Cool-11/Computational-Power-Scheduling.git`）。

## 二、先写规格，再写代码

### 2.1 固定协议与时间线

以如下顺序作为唯一的 tick 状态机：

`读取 TICK → 按输入顺序处理全部事件 → 计算并输出 ANS → 按输出顺序应用 RUN/KILL/DROP → 输出 END 并刷新`

明确以下边界：

- `DONE`、`FAIL` 等事件发生在该 tick 的对账之前；本轮 `RUN` 发生在对账之后。
- 作业从启动 tick `s` 占用资源，释放于 tick `r`；运行费为 `cpu × 机房单价 × (r-s)`。仍在运行的作业回答 `BILL` 时，计费截至当前 tick `t`。
- 第 `T` 轮结束仍运行的作业，最终利润按 `T+1` 释放计费；这与第 `T` 轮对账时的费用边界不同。
- `DONE` 只由输入事件确认，不能凭估计时长自行完成作业。`RUN` 时也不知道真实时长。
- 对账答案必须根据**指令执行前**的状态产生；生成指令时则必须逐条更新内部状态，保证下一条仍合法。

先形成一份规格表：每种事件修改哪些状态、每种对账读取哪些状态、每种指令检查并修改哪些状态。实现和测试都以该表为准。→ `docs/规格表.md`

### 2.2 状态与数据结构

| 子系统 | 主要状态与结构 | 选择理由 |
|---|---|---|
| 工作流、作业 | 9 位外部 ID 用哈希表映射到连续下标；作业数组保存状态、前驱、后继、机器、启动 tick；工作流保存拓扑输入顺序、完成数和收益参数 | 避免按巨大 ID 开数组；便于遍历和计算 DAG |
| 租户与配额 | 父节点数组、当前配额、子树在用 CPU；`QUOTA/UNDO` 用栈记录 `{租户, 旧配额}` | 祖先链最多 200，启动与释放时沿父链更新，`HEAD` 沿父链求最小值 |
| 账单 | 每个租户维护其子树的已结算费用、运行中费率、运行中截距；费用发生或作业释放时沿祖先链更新 | `BILL(o,t) = 已结算费用[o] + t × 运行中费率[o] + 运行中截距[o]`，可直接回答 |
| 网络 | 邻接表、链路开关、机房开关；拓扑变化时增加版本号；按需从机架节点跑 Dijkstra，并按版本缓存结果 | 链路和机房状态动态变化，机架最多 30 个，按需缓存可复用对账与调度所需距离 |
| 两级镜像缓存 | 每台机器、每个机架分别维护“层 → 位置”的索引和 LRU 双向链表，另存已用容量 | 精确支持命中移动、逐层插入和从最久未使用端淘汰 |
| 日志告警 | 以权重和编号共同决定优先级的小根堆构造 Huffman 树；Aho–Corasick 自动机计算模式匹配分；每台机器用按 tick 聚合的滑动窗口 | 保证编码树唯一、重叠匹配正确，并快速回答 `ALARM` |
| `SLACK` | 利用工作流作业的输入拓扑顺序，在未完成子图上正向算 `ES`、反向算 `TL`；按工作流完成版本缓存 | 避免每道重复查询重算，也符合题目对运行中作业仍使用完整估计时长的定义 |

费用使用至少 64 位整数保存，乘法中间结果使用更宽类型并检查范围。容量、距离、费用、时间分别命名和封装，避免混用。

### 2.3 必须锁定的规则细节

- **网络**：`ROUTE(a,a)` 仅在节点正常时为 `0`；节点停电时仍不可达。`RUN` 对同机架输入无需传输，因此这份输入不做路由检查。机房停电只禁用其网络节点；机器是否故障由 `FAIL/UP` 单独决定。
- **缓存**：镜像层严格按底层到顶层处理。机器命中只更新机器 LRU；机架命中更新机架 LRU 后放入机器；两级都未命中则先放入机架、再放入机器。每次插入后立即淘汰。大于缓存容量的层即使立刻被淘汰，也已发生相应拉取量与费用。
- **故障**：`FAIL` 中断该机器所有运行作业、结算至当前 tick 的运行费、释放资源并清空机器缓存；机架缓存保留。`UP` 后机器缓存为空。`KILL` 同样结算并释放，但不清空缓存。
- **账单与配额**：拉取费和传输费在 `RUN` 时发生，已经发生的费用不因 `KILL`、故障或 `DROP` 退还。配额下调至低于当前用量是允许的，但随后启动仍须逐级满足新配额。
- **DAG**：`DONE` 后才解除后继的依赖。`SLACK` 只在未完成作业构成的图上计算，运行中作业仍按完整估计时长计算；重复模式串和重叠告警出现次数均须累计。
- **指令**：`DROP` 时工作流不能有运行作业；同 tick 的 `RUN/KILL/DROP` 必须按输出顺序模拟。每 tick 不超过 20000 条指令。`nq=0` 时仍输出单独的 `ANS` 行。
- **交互读写**：避免等待输入填满固定大缓冲才返回的读取方式；使用适合管道交互的快速读入，并在每轮 `END` 后显式刷新。解析 `WF` 时继续读取其后 `n` 行作业，不能把它们算作额外事件。

## 三、实施步骤与每阶段验收

1. **建立仓库与证据目录**：在空仓库中建立 `src/`、`tests/`、`docs/`，记录 OJ 题面版本、样例压缩包来源、编译命令与环境。使用给定 SSH 地址作为 `origin`；推送前检查远端和待提交文件。提交物保留可直接用于 OJ 的单文件 C++17 版本。
2. **完成交互骨架**：只解析初始化、tick、事件和问题，输出正确数量的占位答案、`END` 并刷新。先验证不会卡住、错位或提前退出；随后移除占位答案。
3. **实现确定性状态机**：依次完成作业生命周期、机器资源、租户配额和撤销、费用、网络、缓存、日志、`SLACK`。每完成一个模块，写独立小场景验证其状态变化和边界，再接入完整交互。
4. **完成七类对账**：对同一状态重复提问应得到一致答案；网络状态变化、多个同 tick 事件、重复查询和时间边界都要覆盖。先以不发 `RUN` 的版本建立协议和静态对账基线，再用可控的少量 `RUN` 验证动态对账。
5. **加入保守合法调度**：维护待运行且前驱已完成的候选集。每条 `RUN` 前检查作业状态、工作流状态、机器健康与剩余资源、整条祖先配额链、所有需传输输入的可达性；应用指令后立即更新资源、费用与缓存。默认不使用 `KILL`，仅在确定无运行作业且预计继续执行无收益时使用 `DROP`。
6. **逐轮改进利润**：先按估计完成时间、工作流剩余关键路径、价值、运行成本、传输和拉取准备时间形成候选排序；再比较机器选择中的数据位置、镜像热度、机房单价和故障风险。每次只改一个策略因素，固定随机种子比较利润构成、完成工作流数、非法指令数和运行耗时；无稳定收益的改动回退。
7. **性能与提交**：在正式规模参数下检查峰值内存低于 256 MB、总运行时间有余量，并针对最坏输入量检查读写。提交前本地跑通两个样例及多组随机世界，保存每次实验的参数、版本、结果和第一处错误。OJ 仅有 10 次提交机会，按验证过的里程碑提交，不把 OJ 当主要调试器。

## 四、测试矩阵与常见陷阱

**正确性小场景**至少包括：

- 同 tick `DONE` 后对账、`FAIL` 与 `DONE` 顺序、`UP` 后空缓存、`KILL` 后再次 `RUN`、`DROP` 的有运行作业限制。
- 配额连续修改与多次 `UNDO`，配额低于既有用量，父租户与子租户同时受限。
- 同机架输入、不同机架同节点、断链、机房停电、恢复后路由更新，以及不可达返回 `-1`。
- 镜像重复层、跨镜像共享层、机器命中、机架命中、仓库拉取、插入即淘汰和容量恰好相等。
- Huffman 频数相同的编号裁决、十六进制最后补零位忽略、模式重叠、重复模式、窗口首尾 tick。
- 分叉与汇合的 DAG、前驱完成后子图改变、运行中作业查询 `SLACK`、同工作流重复查询。
- `ANS` 问题顺序、零问题、零指令、连续多轮和末轮退出。

**验证方法**：为费用、缓存、路由和 DAG 各写一个独立、易读的慢速参考实现，用小随机场景做差分比较；完整交互使用题目提供的本地评测程序，以“第一处对账错误／第一次非法指令”为定位入口。样例中的固定答案依赖样例给出的历史指令；如果自己的指令不同，后续答案不能直接逐行与样例文本比较。

**性能重点**：最多 6 万作业、3500 道对账、3 MB 解码日志和动态网络；不要对每道 `SLACK` 扫描全部工作流，也不要对每条候选调度反复重跑最短路。给网络缓存设置拓扑版本，给 `SLACK` 设置工作流完成版本；策略每轮先排序候选，再限定重点评估数量，记录耗时后调整。报告中同时保留基线与改进策略的可复现实验数据，不能只写最终分数。

## 五、假设与记录要求

- 以用户提供的完整 OJ 题面为规则依据；计划中的示例参数不是正式数据保证。
- 实现语言为 **C++17**，文档定位为**开发执行手册**。若 OJ 编译选项有额外要求，在建仓阶段核实并记录。
- 调度算法没有标准最优解；优先级是“对账全对、零非法指令、再提高利润”。不以全部 100 组通过为验收目标。
- 课程设计独立完成。开发日志应记录本人做出的结构选择、错误定位、策略迭代和 AI 工具具体参与内容，最终报告与实际代码、测试结果保持一致。
