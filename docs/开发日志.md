### 0. 起点与约束

- 本地没有任何 C++17 编译器（只有 Dev-C++ 的 TDM-GCC 4.9.2 和 miniconda 的 C 编译器），
  按用户选择在 `D:\msys64` 安装 MSYS2 + mingw-w64 g++ 16.2.0。
- OJ 只回传分数，拿不到官方样例压缩包（`tpj_win.exe`），所以**本地评测器必须自己写**。

### 1. 先做「能验证」的东西，而不是先堆功能

题面给了样例 1（10 tick）和样例 2（40 tick）的**完整交互记录**：事件、对账题、官方答案、
官方指令流都在里面。这比任何单元测试都值钱，因为它同时覆盖了七类对账和全部事件类型。

于是顺序反过来：

1. 把样例原文存成 `tests/samples/sample{1,2}.txt`；
2. 写 `tools/judge.py`（Python 慢速参考实现），支持「字面回放」官方记录；
3. **先用官方 100 道答案把参考实现钉死**（结果 100/100 一致），再写 C++；
4. C++ 只用同一个参考实现做差分测试。

这样做的收益在后文直接体现：C++ 里三个致命 bug 都是「答案和参考实现不一致」暴露的，
不需要猜。

### 2. 结构选择

| 决策 | 选择 | 理由 |
|---|---|---|
| ID 映射 | `unordered_map<int,int>` | 外部 ID 是 9 位整数，直接开数组需要 1G 空间 |
| 作业存储 | 连续 `vector<Job>`，工作流的作业在数组里连续 | `SLACK` 只需扫 `[job_begin, job_end)`，且天然是输入拓扑序 |
| 租户链 | 父指针数组 + 沿链遍历（深度 ≤ 200） | 比维护子树索引简单，且和账单/配额公式一一对应 |
| 账单 | `settled + rate*t + inter` 三元组 | 运行费可以 O(1) 回答，不用每次遍历运行中作业 |
| 镜像缓存 | 每台机器/每个机架各一组「层 → 前驱/后继」稠密数组 | 层 ≤ 400、缓存 ≤ 390，稠密数组只有 ~1.7 MB，比链表+哈希快得多 |
| 网络 | 邻接表 + 按 (拓扑版本, 源节点) 缓存的 Dijkstra | 机架 ≤ 30，一条最短路 600 节点，缓存后对账和调度都是查表 |
| 告警 | 每 (机器, tick) 稠密数组 + 滚动窗口和 | 对账只要 W ≤ 60 次加法；比维护环形缓冲区的边界逻辑简单 |
| 自动机 | 9 列的定长转移表（`a~h` + `_`） | 状态数 ≤ 模式总长，转移是一次数组下标 |

### 3. 踩过的坑（按发现顺序）

1. **Huffman 建树选错了最小值**：`alive[]` 里存的是树编号，但比较时把「数组下标」当成了权重，
   导致同样频数下的取舍和题面不一致，解码出的符号串整体错位。
   症状是 `ALARM` 随机地大 2 倍或完全为 0。改成显式维护 `alive[pa]` / `alive[pb]` 后消失。
2. **告警窗口只做懒过期**：环形缓冲区只在「同一槽位再次写入」时才减去旧值，
   若中间若干轮该机器没有日志，旧值就一直留在窗口和里。
   改成每 tick 结束时统一减去 `t-W` 那一行。
3. **`SLACK` 把外部 ID 直接当下标**：样例世界里作业数组只有几十个元素，
   `jobs[100000152]` 直接越界崩溃（0xC0000005）。
   所有外部 ID 入口都必须走 `job_id.find`。
4. **就绪表会吞掉「还没准入」的作业**：调度每轮重建就绪表时，把不可运行的一律丢弃，
   于是工作流稍后被准入时它的作业已经不在表里，永远跑不起来。
   症状是大世界里 CPU 占用率 2%、`inflight_demand` 卡住不动。
   改成「只有 dead/finished 才丢，未准入的留着」。
5. **评测器把 DONE 处理了两次**：作业被 KILL 后重跑，两次运行都可能排到同一个完成 tick，
   `due` 里出现两条记录，都被判定为「该 tick 完成」，后继的 `rem` 被减成 -1。
   我方程序反而没错（对非运行中作业的 DONE 直接忽略），是评测器自己把状态搞坏了。
   修正：DONE 只对运行中作业生效 + 同 tick 去重。
6. **评测器算总费用时把每个租户的账单加了一遍**：`BILL` 是子树和，
   把 K 个租户相加会把同一笔费用重复计算（深度倍）。改成只取根租户在 `T+1` 的账单。

### 4. 调度策略的演进

见 `docs/实验记录.md`。最重要的一条结论：

> 在这个题里，「多跑」不等于「多赚」。拉取费和传输费在 `RUN` 时就扣掉、
> 而且 KILL/FAIL/DROP 都不退，所以**一次错误的准入就是纯亏损**。
> 早期版本把机器全塞满（利用率 65%），利润是 -22 万；
> 改成严格准入 + 只跑能按时完成的工作流（利用率 15%）后利润转正。

具体做法：

- **准入**：到达时估关键路径（用自适应系数把估计时长放大到接近真实时长，再加上每作业的
  准备时间），只有「预计完成时间 ≤ min(截止 + 宽限, T)」且「收益 > 1.5×成本」才准入；
  同时检查租户配额余量、在飞工作量是否超过 `核数 × 2`。
- **排序**：就绪作业按「松弛时间」升序，最紧的先跑。
- **选机器**：先算出每台机器的预计完成 tick，只在「比最快慢不超过 1 tick」的机器里挑总成本
  （传输 + 拉取 + 运行费）最低的——这样既不会为了省钱拖死截止时间，也不会为了快而付昂贵的传输费。
- **止损**：工作流用乐观估计都已经赶不上时，`KILL` 掉它正在跑的作业，把资源让出来。
- 不使用 `DROP`：它的效果（不再执行待运行作业）用「不调度」就能等价实现，少一条可能出错的指令。
