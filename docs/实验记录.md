# 实验记录（策略迭代）

所有数字都可用本仓库脚本复现：

```bash
# 16 个 60 tick 的随机世界（同一批 seed，含失败/停电/断链/配额事件）
python tools/bench.py --tag 版本名 --seeds 1-16 --T 60

# 接近正式规模的世界（T=200，11k 作业）
python tools/judge.py run --world tests/worlds/big1.in --solver build/solver.exe

# 满规模世界（T=600，48k 作业，3600 道对账）
python tools/judge.py run --world tests/worlds/huge.in --solver build/solver.exe
```

世界由 `tools/gen_world.py` 生成（`--seed` 决定），评测由 `tools/judge.py` 完成；
`judge.py replay` 用官方样例的 100 道对账校验参考实现本身（结果：**100/100 一致**）。

## 四、结论

1. 对账与合法性在 20 组世界 + 2 个官方样例上全部通过，可以认为状态机正确。
2. 利润的主要来源是「只跑那些能按时完成、且收益覆盖成本的工作流」；
   主要风险是**沉没成本**（拉取/传输费不退），所以要严格控制准入。
3. 拉取费和传输费在很多世界上比运行费还高，因此机器选择必须把
   「数据在同机架 / 镜像已缓存」放在与完成时间同等重要的位置。

## 五、按官方参数文件重建世界（关键转折）

前四节的结论都建立在“我自己随便造的世界”上。拿到题面里的参数样例后，
按同样的参数名生成世界（`tests/params/oj.in` → `tests/worlds/oj.in`：T=500、4 机房、
20 机架、189 台机器、120 租户、300 层、80 镜像、8045 个模式串、load 0.9、audit 3.5），
结论立刻变了：

| 版本 | 关键改动 | 完成/总数 | 收益 | 费用 | 利润 |
|---|---|---|---|---|---|
| a | 之前的策略（按"最好准备时间"估算完成） | 266/2145 | 440418 | 940379 | **-499961** |
| b | 把传输费/拉取费按下界计入准入成本 | 386/2169 | 697928 | 560657 | +137271 |
| c | 收益门槛 200% | 422/2169 | 820662 | 461362 | +359300 |
| d | 收益门槛 300% | 384/2169 | **820978** | **255582** | **+565396** |
| e | 收益门槛 400% | 286/2169 | 646623 | 152388 | +494235 |

费用结构（版本 d）：运行 100692 + 拉取 125842 + 传输 29048。
**拉取费比运行费还高**——这是这类数据的关键特征：一个作业从仓库拉镜像的钱，
可能等于它跑完全程的 CPU 钱。所以“镜像是否已在该机架缓存”必须进入决策，
否则跑得越多亏得越多。

这也解释了为什么不能盲目堆并发：在这个世界里，平台的 CPU 是富余的（占用率 2.6%），
真正的瓶颈是**每跑一个作业要付的固定成本**。收益门槛 300% 时完成的 384 个工作流
平均收益 2138、平均费用 665；门槛放到 150% 会多跑一批"赚不回本"的工作流，
利润反而从 56 万掉到 13 万。

> 注意：门槛是**相对值**（收益 ≥ 成本 × 300%），而成本里的传输项用
> “机架间平均距离”实测得到。所以换到距离更近、单价更低的正式数据时，
> 同一个门槛会自动放宽，不会因为写死而变得过度保守。

### 关于“高并发”

起初我把“多跑”当成目标，实测反而更差；后来意识到要区分两件事：

- **平台容量**：本世界里 189 台机器、~1700 核，占用率长期在 3%~7%，远没到瓶颈；
- **单位作业的固定成本**：拉取 + 传输，占了总费用的 60%，且发生即沉没。

所以在 CPU 富余的世界里，正确的“高并发”不是把机器塞满，而是
**把并发的额度花在单位成本最低、收益最高的那批工作流上**。
如果真的遇到“容量才是瓶颈”的数据（成本低、价值高），门槛会自动放行更多工作流，
此时调 `ADMIT_HORIZON` 才会起作用（它现在基本不 binding，因为准入才是闸门）。

## 六、拿到官方评测程序之后（结论推翻重来）

用户提供了样例压缩包（`1846_samples.zip`），里面有 `tpj_win.exe` —— **它才是真正的平台**：
读参数文件 → 生成世界 → 通过标准输入输出跟程序对局，跑完直接打印

```
对账错误 0/1767，非法指令 0，利润 4718943（目标 无）。收益 7666905，运行费 2080911，
拉取费 378328，传输费 488723，上界 U=17427102。工作流 2194 个，完成 1112（按时 1075，逾期 37）…
```

`tools/tpj_run.py` 就是把它接到本地求解器上的双向管道。有了它，前五节的“调参”全部作废——
因为我造的世界和官方生成器的经济结构根本不同。

### 6.1 第一个发现：并发预算是唯一大杠杆

官方参数、D=4、182 台机器、30612 个作业、500 tick：

| 在飞预算 `ADMIT_HORIZON` | 利润 | 完成工作流 |
|---|---|---|
| 2（旧默认） | 764820 | 305/2194 |
| 8 | 1299089 | 450/2194 |
| 20 | 2735259 | 778/2194 |
| 50 | 4374109 | 1064/2194 |
| 100 | 4749956 | 1111/2194 |
| 300 | 4749956 | 1111/2194 |

**同一条代码、只改一个预算，利润差 6 倍。** 原因：旧版本在工作流队列里把 1889 个工作流
“排到过期”——平台有 3176 个核，我们只用了 1.4%，因为准入预算按“Σc·e”卡死，
最多只放 28 个工作流同时在场。

### 6.2 第二个发现：收益门槛的最优值从 300% 掉到 150%

在高并发的前提下重扫：

| 收益/成本门槛 | 利润 |
|---|---|
| 0%（只判可行性） | 2448253 |
| 100% | 3134834 |
| **150%** | **4749956** |
| 200% | 2250081 |
| 300%（旧默认） | 559331 |

门槛太低会把“赚不回本”的工作流塞满队列（它们挤掉高价值工作流）；
太高则大量有利润的工作流被拒。150% 是这台天平的最优点，三个 seed 上都是。

### 6.3 最终成绩（官方评测程序，0 对账错误 / 0 非法指令）

| 世界 | 规模 | 利润 | 上界 ub3 | 完成 |
|---|---|---|---|---|
| seed 20261105（题面给的参数） | T=500、182 机、30612 作业 | **4718943** | 17427102 | 1112/2194 |
| seed 11 | T=500、177 机、20283 作业 | 1267652 | 8097183 | 614/1426 |
| seed 22 | T=500、163 机、26324 作业 | 4969211 | 17117789 | 985/1865 |
| seed 777（满规模） | T=600、356 机、83026 作业 | 5809724 | 39350096 | 1883/5806 |

满规模那组：3567 道对账全对，求解器单独计时 **0.65 s**（8.3 MB 输入），内存 < 40 MB。

> 与上界的差距（约 27%）主要来自“我们不知道真实时长和未来故障”，
> oracle 能提前放弃注定超期的工作流，我们只能靠估计 + 止损。

### 6.4 教训

同一个策略在两类世界里结论相反，原因只有一个：**我早期造的世界上传输/拉取贵得离谱**
（机房内 90 节点大环，机架间平均距离 15~27 tick），于是“少跑少亏”；
而官方世界的机架间距离只有几 tick，平台又大，此时“跑满 + 挑单”才是对的。

结论：**不要用自己的模拟器给策略定型**。能拿到官方评测程序，就一定用它做决策依据。

## 七、用官方评测器做的一轮"抠利润"

有了 `tpj_run.py`，每次实验 ~2 秒，可以并行跑 4 个 seed。这一段记录按官方评测器
（`tools/eval_oj.py`，4 个 seed：题面参数 + 11 + 22 + 33）做的所有尝试。

### 7.1 有效的改动

| 改动 | 合计利润 | 说明 |
|---|---|---|
| 起点（第六节结论） | 12,893,525 | H=100、门槛 150% |
| **按租户估真实时长**（题面说偏差与租户有关） | **13,210,632** | 每个租户单独维护 dur/e，准入的完成时间估计更准 |
| 止损改成每 tick 检查 | 13,269,946 | 早 1~2 tick 杀掉必败的工作流，少烧预置费 |
| 止损只扫"有运行中作业"的工作流 | 13,137,885 | 同利润、省 0.06 s（最终采用） |
| 验证"主场机架"值多少：关掉它 | 12,856,396 | 关掉掉 2.2%，说明钉主场（省传输、省重复拉镜像）确实有用 |

最终：seed1 4.77M / seed11 1.35M / seed22 5.00M / seed33 2.01M，合计 **13,137,885**，
四组都是 0 对账错误、0 非法指令。

### 7.2 试过但更差的（都回退了）

| 尝试 | 利润 | 为什么会差 |
|---|---|---|
| 用"实测平均成本"替代公式估成本 | 8,636,152 | 幸存者偏差：只能观测到被选中的便宜工作流，于是越估越低、越放越亏 |
| 等镜像缓存热了再跑（冷拉取就等） | 4,775,019 | 死锁：没人拉就没有热的，全平台卡住 |
| 主场机架按整条链总成本选 | 9,160,794 | 只看静态成本，忽略机器并行度与单价，链被塞进一台空闲机的机架 |
| 热点机架偏好（缓存热度） | 12,365,497 | 把负载堆到少数机架，反而排队 |
| 单工作流"传输+拉取"预算上限 | 12,928,079 | 与准入门槛重复，只多了一点约束 |
| 机器选择改成 max(收益−成本−占用代价) | 13,045,322 | 时间维度没估准，反而不如"先比完成时间再省钱" |
| 降低成本估计里的"未命中率"（放行更多） | 7.6M~10.3M | 边际工作流确实亏钱，门槛是准的 |
| 就绪作业改按价值 / 进度排序 | 12.97M / 12.91M | 松弛时间优先仍最好 |

### 7.3 现在钱花在哪（seed1）

```
收益 7,672,148   运行费 2,081k   拉取费 378k   传输费 489k   中断浪费 112k
利用率 33.5%    其中 26% 的核·时间是在等数据/镜像（传输 84k、拉取 72k 核·tick）
实际均价 3.82 /核·tick（最低 2）——便宜的机房被抢空后只能退到贵的
```

三个明确的浪费点：**等准备的 26% 核时、均价高出最低价 91%、以及 843 个被判"不划算"而没接的单**。
前两个都试过改（延迟换便宜机房、等热镜像、按链成本选机架），但都会连带牺牲截止时间，
净效果为负。第三个是信息劣势：不知道真实时长，只能用悲观估计筛。

### 7.4 结论

利润的大头来自结构（第六节：并发预算 ×6、门槛 ×8），这一轮参数级优化只再挤出 **+1.9%**。
继续提升需要换思路（例如按镜像聚簇调度、或对"边际工作流"做在线学习），
而不是继续调这几个旋钮。

## 八、镜像聚簇：认真试了，结论是"在这份数据上不划算"

用户提示"考高并发"之后，第六、七节把并发和门槛调对了。这一节专攻**镜像缓存命中率**。

### 8.1 先量清楚问题有多大

debug 统计（seed1，最终配置）显示：

```
冷拉取 1956 / 9324 次（21.0%）        共 170455 字节
准备时间拆分：传输 95834 / 拉取 110625 核·tick（prep 占总核时 27.9%）
```

也就是 79% 的 RUN 已经命中缓存了。剩下的 21% 冷拉取，最多能省
`170455×U_reg ≈ 341k` 的拉取费 + `110625 核·tick ≈ 420k` 的等待成本。
**上限大约 760k，相当于利润的 15%**——值得试，但不是决定性的。

### 8.2 试过的四种聚簇方式（全部更差）

| 做法 | 合计利润 | 为什么崩 |
|---|---|---|
| 镜像专属机架：镜像 i 固定去机架 `i*R/I`，优先放那里 | **-10,797,384** | 机架和输入的相对位置完全脱钩，传输距离暴涨，直接把利润做成负数 |
| 机器选择加"镜像已热"让价 `WARM_BONUS`=100/300/600 | 12.30M / 12.58M / 12.73M | 只奖励当下热的机架，热机架很快被占满，反而多跑冤枉路 |
| 选主场机架时按 25%/50%/100% 计入"镜像冷不冷" | 13.31M / 12.11M / 10.56M | 与"按输入距离选主场"冲突：为了省一次 3 tick 的拉取，把整条链搬到离输入很远的机架 |
| 选主场时计入机房单价（去便宜机房） | 13.88M / 13.69M / 11.37M | 便宜机房很快被抢空，随后只能排长队 |

### 8.3 为什么不行

把两个"每作业"的量放在一起比就清楚了：

- 冷拉取的代价 ≈ `ceil(镜像字节/B_reg) ≈ 3 tick` 的核时 + `字节×U_reg ≈ 175` 的钱；
- 跨机架传输的代价 ≈ `dist + ceil(z/B_net) ≈ 5~8 tick` 的核时 + `z×dist×U_net` 的钱。

在这份数据的网络里，**传输比拉取贵**。所以"按镜像聚簇"每省一次拉取，往往要多付一次更贵的传输。
真正的最优是反过来——**按输入聚簇**，也就是第七节做的"按整条链的输入距离选主场机架"。

### 8.4 这一节真正的收获

不是镜像聚簇，而是一个更准的主场机架规则（`HOME_MODE=3`）：

```
主场机架 = argmin_r [ Σ_jobs (z_in × dist(r, src_rack) × U_net) ]，
           并对"只剩 1 台空闲机"的机架加 10000 的惩罚、对空闲机器多的机架减 30/台
```

| 版本 | 合计利润 |
|---|---|
| 起点（首个作业的最佳放置定主场） | 12,893,525 |
| 改为按整链输入距离 + 容量偏好 | 13,539,545 |
| 再把收益门槛从 150% 调到 140% | **14,033,873** |

seed1 从 4,718,943 提到 **5,057,578**（完成 1110 → 1182），四组全部 0 对账错误、0 非法指令。

## 九、分层调度（先把便宜机房填满）：又是一条死路

思路很自然：机房单价从 2 到 6，差 3 倍，那我们先把便宜机房塞满，溢出了再去贵的。

### 9.1 严格分层（按单价排序，逐层尝试）

```
收益 3,223,654   运行 3,396,198   传输 3,180,639   拉取 917,558   → 利润 -4,270,741
完成 566/2194（平时 1182），上界 17,427,102
```

**传输费从 49 万炸到 318 万**，直接把利润做成负数。原因很硬：

- 机架到机架的距离是 5~8 tick，跨机房更远；把作业按单价赶到便宜机房，等于让它离输入数据很远；
- 每个作业能省的运行费 ≈ `(6-2) × c × dur ≈ 4×4×5 = 80`，
- 但它要多付的传输费 ≈ `z × dist × U_net ≈ 16×8×1 = 128`。

**省 80、赔 128，越"省钱"越亏。** 而且便宜机房只有约 1/4 的机器，一塞就满，后面的作业只能排队等截止。

### 9.2 软一点的做法也都不行

| 做法 | 利润 |
|---|---|
| 主场机架只在"距离差 10% 以内"时才选便宜机房 | 6,020,107 |
| 选主场时把运行费按 25% / 50% / 100% 权重计入 | 13,880,989 / 13,690,112 / 11,369,016 |
| 机器选择时加"镜像已热"让价 | 12.30~12.73M |

### 9.3 结论

价格维度在这份数据上**不可优化**：便宜机房既是稀缺资源（1/4 机器），又与数据分布正交。
现在的 3.77 均价（最低 2）不是选择失误，而是"数据在哪、机器就得在哪"的必然结果。

第七节的 14,033,873 仍是目前最好成绩。要把利润再抬一个台阶，只剩两条路：

1. **提高完成数**（现在 1182/2194），需要更准的"这个工作流能不能按时完成"判断；
2. **降低准备时间**（27.9% 的核时在等传输/拉取），需要更好的机架与镜像协同——
   但第八、九节已经证明，简单地把同类作业聚在一起会更差，必须做成"按输入为主、镜像为辅"的加权，
   而这两者的权重又与具体网络相关，容易过拟合到本地 seed。
