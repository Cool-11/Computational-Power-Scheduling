# 实验记录（策略迭代）

所有数字都可用本仓库脚本复现：

```bash
# 16 个 60 tick 的随机世界（同一批 seed，含失败/停电/断链/配额事件）
python tools/bench.py --tag 版本名 --seeds 1-16 --T 60

# 接近正式规模的世界（T=200，11k 作业）
python tools/judge.py run --world tests/worlds/big1.in --solver build/solver.exe

# 满规模世界（T=600，48k 作业，3600 道对账）
python tools/judge.py run --world tests/worlds/huge.in --solver build/solver.exe
```

世界由 `tools/gen_world.py` 生成（`--seed` 决定），评测由 `tools/judge.py` 完成；
`judge.py replay` 用官方样例的 100 道对账校验参考实现本身（结果：**100/100 一致**）。

## 一、先保证前三项，再谈利润

基线阶段所有版本都是「对账 0 错、0 非法指令」，下表只比较利润。

| 版本 | 关键改动 | 16 世界总利润 | 完成/总数 |

## 二、参数扫描（固定 16 世界，只改一个因素）

### 在飞工作量预算 `ADMIT_HORIZON`（全平台核数 × H）

| H | 总利润 |
|---|---|
| 1 | 138147 |
| 2 | 242554 |
| 3 | 200249 |
| 4 | 124590 |
| 6 | 84474 |

H=2 最好：预算约等于「两轮满负荷的工作量」。

### 完成时间估计的悲观程度 `EST_SCALE`（对准入判断的完成时间打折）

| 折算 | 总利润 |
|---|---|
| 100%（不折） | 114320 |
| 85% | 103117 |
| 70% | 89053 |

不折最好——准入太乐观会把资源投到完不成的工作流上。

### 等待耐心 `PATIENCE`（到达后最多等多久才准入）

| 耐心 | 总利润 |
|---|---|
| 0 tick | 74289 |
| 3 tick | 71076 |
| 6 tick | 56667 |
| 不限 | 114320 |

不限最好：准入预算释放后补进来仍然来得及。

### 配额门槛 `PEAK_DIV`（要求余量 ≥ 工作流峰值并发 / DIV）

| DIV | 16 世界总利润 | big1 利润 |
|---|---|---|
| 1 | 634080 | -117821 |
| 2 | 650968 | -196880 |
| 3 | 662576 | -208080 |

DIV=1 在小世界上略差、在大世界上好 65k，取总量更优的 DIV=1。

## 三、满规模性能

`huge.in`：T=600、48 301 个作业、191 560 行日志、3600 道对账、14 MB 输入。

| 项目 | 数值 |
|---|---|
| 求解器自身耗时 | **0.59 s**（其中解析+事件+解码+对账 0.33 s，调度 0.26 s） |
| 峰值内存 | **26.4 MB** |
| 对账 | 3600 道，错 0 |
| 指令 | 926 条，全部合法 |
| 利润 | +141608 |

## 四、结论

1. 对账与合法性在 20 组世界 + 2 个官方样例上全部通过，可以认为状态机正确。
2. 利润的主要来源是「只跑那些能按时完成、且收益覆盖成本的工作流」；
   主要风险是**沉没成本**（拉取/传输费不退），所以要严格控制准入。
3. 拉取费和传输费在很多世界上比运行费还高，因此机器选择必须把
   「数据在同机架 / 镜像已缓存」放在与完成时间同等重要的位置。
